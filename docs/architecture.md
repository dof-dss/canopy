# Architecture

## Boundaries

Canopy observes technical state and produces evidence. It does not remediate
findings. Checks should be useful in a developer terminal, in DDEV, and in CI
without assuming a central service exists.

Static inspection is the default. Database, container, network, browser, and
hosting access are separate capabilities which a caller must explicitly allow.

## Layers

1. **Discovery** identifies the project, Drupal sites, exported configuration,
   services, and available tools.
2. **Adapters** collect bounded evidence from files, Composer, Git, Drush,
   DDEV, Solr, or other explicitly permitted sources.
3. **Checks** evaluate evidence against deterministic rules or selected
   capability profiles.
4. **Results** record stable statuses, targets, evidence, limitations, and
   optional manual remediation.
5. **Renderers** produce versioned JSON and human-readable reports.
6. **Prompts** interpret completed result documents without changing their
   status or substituting for checks.

Prompt workflows may guide explicitly confirmed local preparation, but they do
not grant repository publication authority. AI-driven workflows must never
stage, commit, push, create a pull request, tag, merge, or publish code. A
developer must review and perform those actions. Every state-changing local
phase requires a separate, specific human confirmation and must preserve
pre-existing worktree changes.

Canopy provides a foundation on which agentic services can support these
processes; it does not mandate a particular agent, model, editor, or automation
platform. Developers should use tools appropriate to their context, role, and
authority. Any tool consuming Canopy prompts or evidence must discover and
respect the applicable `AGENTS.md` directives for the repository and working
directory, alongside the prompt's own safety boundaries and the developer's
instructions.

## Expected versus observed state

Canopy may consume expectations generated by Maestro or another project
template, but it remains independent of those tools. Generated expectations
describe intended state; Canopy records observed state and discrepancies.

## Initial Solr slice

The first implemented slice is a static Solr audit because it exercises the
main architectural boundaries:

- static and runtime evidence;
- Drupal multisite discovery;
- DDEV and hosted connector differences;
- configset fingerprints;
- infrastructure, Drupal integration, indexing, and capacity as separate
  readiness dimensions;
- explicit handling of stale persistent local cores;
- comparable output across several projects.

It currently performs repository-only checks and can explicitly execute a
known project-owned static verifier. Optional DDEV, Drush, and Solr adapters
remain future work and must sit behind explicit permissions.
